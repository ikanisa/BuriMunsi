# Android receiving phone and member statement acceptance

An authorized receiving Admin and an operator with access to the same group's Payments can run this on the approved physical handset. Allow normal carrier traffic to supply the evidence. Use a receipt whose owner has approved this check. Keep raw messages, names, phone numbers, passcodes, carrier identifiers and complete statements inside the authorized case system.

## Establish the baseline

1. Record the UTC start time, application ID and version on the phone. The receiver is `rw.ikanisa.burimunsi.gateway.cloud`. The separate Staff application is `rw.ikanisa.burimunsi.staff.cloud`. For an already authorized ADB connection, run `python3 native/burimunsi/scripts/physical_receiver_preflight.py`. With multiple handsets, select the intended one with `--serial`. The output contains the foreground user's installed versions. The operator confirms physical custody, approved build and the signed-in role separately.
2. In Admin Sync, open **Account → Gateway**. Confirm the intended group, current Admin access, approved sender, Android SMS and phone permissions, and initial queued count. Record the state of the receiving SIMs and notification permission. Use a private case alias for each SIM. An Admin observation installation can receive on either active SIM when Android identifies the actual source. An existing paired gateway keeps its original SIM binding.
3. Choose a previously authorized live reference for the statement check and witness a naturally arriving carrier receipt for live delivery. A historical receipt alone cannot demonstrate a new broadcast. If a required case has no naturally arriving receipt, leave that case open. Keep the installed application and the provider's original message throughout the check.

## Observe continuity and source holds

| Case | Action on the authorized test handset | Evidence to record |
| --- | --- | --- |
| Locked and backgrounded | Lock the phone with the Admin session current. When a genuine approved receipt arrives, record carrier and application times, then unlock and inspect the authorized receipt. | Delivery, original source, and a single matching payment. |
| Data offline | Turn off Wi-Fi and mobile **data**, keeping the receiving SIM and its SMS service active. Observe an incoming receipt, then restore data and open Gateway. Use **Sync** once if needed. | Before/after counts and times, eventual acknowledgement, and one matching payment. A network icon or listening notification alone cannot establish this. |
| Restart / Android force stop | On a designated test handset with permission to interrupt receiving, record the pending state, reboot/unlock, then observe recovery. Run the Android force-stop case separately. Reopen Admin Sync manually after force stop and reauthenticate if requested. | Preserved installation, same signed-in group, original receipt identity and state before/after, and a single eventual payment. A receipt seen only after reopening demonstrates catch-up. |
| Two active SIMs | For each naturally observed approved receipt, verify which SIM the Android provider identified. Keep both SIMs active and compare the two records within the authorized group. | Both verified sources can progress in Admin observation mode. An account or default-SIM setting alone supplies no source evidence. |
| Missing or unverifiable SIM | On a designated handset, observe the approved SIM temporarily unavailable or an eligible source with unresolved Android metadata. Refresh Gateway. When every source is unavailable the updated app reports **SIM source not verified / Blocked**. After its permitted background check observes one unidentified receipt while another SIM is active, it reports **Some receipts are on hold**. | Capture the displayed hold and whether a separately verified receipt progresses. Distinguish an Android inbox row awaiting identification from an already encrypted **Queued** record. A held item can exist with Queued at zero. |
| Restore the original source | Restore the original SIM/permissions and authorized Admin session. Wait for Android to report the source; open Gateway and use **Sync** once. Reopen the app after acknowledgement. | A previously retained request keeps its original ID. Verify correct group/source, one payment, no duplicate after retry and the cleared hold after a complete check. If Android still supplies no source, leave it held and record the exception. |

Use the approved maintenance window for interruptions. Keep app storage and the inbox intact. Selecting the other SIM or the default slot cannot repair missing source metadata. A mixed or unrelated message is outside this acceptance journey.

## Follow the receipt to one member

1. In Admin Sync, open **SMS** and locate the one approved reference. Open its payment when available. Privately record the raw evidence ID, the payment ID, direction, amount, provider reference, time and group. Distinguish parser pending or held states from a completed payment. Any whole-inbox or device-content dump is unnecessary.
2. In **Payments**, open that reference and confirm the same values. Prefer an already allocated receipt with an independently verified member. For a genuinely unallocated item, an operator who has allocation authority may use **Allocate** only for a real, authorized business instruction. The app supplies the version and idempotency key. On an uncertain result, refresh by reference before taking further action. Without authority or a real instruction, leave the allocation step pending.
3. With a permitted operator in the same group, tap the linked member's row in **Payments**. In **Member statement**, confirm the immutable member ID and the one expected reference. Apply a narrow filter and use **Download statement** to save PDF or spreadsheet to approved private storage. Verify the same reference, amount, direction and date and that another member's rows are absent. After a normal sync/reopen, check the payment and statement again for duplicates.
4. Keep only the required proof under the organization's restricted case handling. Record build, UTC times, privately mapped group/SIM/member aliases, queued counts and outcomes, plus access-controlled evidence references or artifact digests. Record each case as observed, failed, or pending with its reason and witness. The existing release guard accepts physical `phone_journeys` and `device_sms_lifecycle` evidence separately. Emulator, host and preflight receipts stay separate from physical carrier acceptance.
