### Other findings from the initial review

The phone/passcode onboarding contract uses a configured initial Staff passcode and supports passcode changes. An independent factor for sensitive actions remains an open product and enrollment item. The project still has no verified external alert recipient or delivery test. The private import stages held 8 and 126 rows at the initial review. Their disposition requires the original data owner’s retention decision. Application clients have no access to the stage schemas. Supabase owns the two `pg_net` transport tables, and the project’s `postgres` role has no grant option for their SELECT privileges. [Product access](../../README.md) · [Initial findings](#priority-1-findings)

The database uses TLS and the Edge Functions use direct PostgreSQL connections. Supabase documents that enabling database IP restrictions cuts off direct Edge access. A restricted egress path would need its own implementation. The independent PostgreSQL and Android qualification environments use synthetic data. A separate hosted Supabase staging branch incurs usage charges and remains unprovisioned. [Connection restrictions](https://supabase.com/docs/guides/platform/network-restrictions) · [Supabase branch usage](https://supabase.com/docs/guides/platform/manage-your-usage/branching)

On 24 November the hosted catalog showed that `collect_runtime`, `collect_sms_runtime` and `collect_importer` cannot log in, bypass RLS or read Vault values. The SMS gateway has a dedicated login with those same privilege restrictions except that it can log in. The core Edge configuration uses the provider-supplied database URL and selects `collect_runtime` inside application transactions. At 11:24 a live PostgreSQL session holding the Collect work-lease lock and running the work-ownership function used TLS and logged in as the hosted postgres role. That login has BYPASSRLS. The application’s transaction role has narrower privileges. Credential rotation and the transition to a dedicated core login remain open.
